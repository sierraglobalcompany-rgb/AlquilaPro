## 1. Resultado F7

F7 implementa un motor contractual privado y mínimo sobre las fuentes canónicas existentes:

`candidate + screening approved + unit → draft → safe preview → immutable snapshot → private PDF + SHA-256 → finalized`

F7 **no** crea tenant, lease, usuario de inquilino, ocupación automática, firma electrónica/digital, segundo auth ni catálogo paralelo.

Tipos V1 implementados:

- `urban_housing`;
- `independent_parking`.

Estados contractuales exactos:

`draft → generated → finalized`

`finalized` es terminal dentro de F7.

## 3. Runtime y PDF

F7 soporta la matriz validada PHP `>=8.3 <8.6`.

Runtime requerido y probado en CI:

- PDO / pdo_mysql;
- mbstring;
- fileinfo;
- dom;
- gd.

Dompdf:

- versión bloqueada por Composer: `3.1.6`;
- remote resources: deshabilitados;
- papel `letter`, portrait;
- DejaVu Sans para UTF-8;
- CSS/header/footer/page numbering internos;
- sin shell, `proc_open`, wkhtmltopdf, Chrome/Chromium ni otro binario externo.

Los PDFs:

- viven en `storage/contracts/`, bloqueado además por `.htaccess`;
- usan nombre físico aleatorio `32 hex + .pdf` sin PII;
- se escriben temporalmente y se verifican antes de rename final;
- límite máximo: `10 MiB`;
- guardan tamaño y SHA-256 sobre los bytes exactos;
- `privatePdf()` vuelve a validar patrón de nombre, realpath, firma `%PDF-`, tamaño y hash;
- la descarga autenticada vuelve a verificar bytes/tamaño/hash antes de responder;
- nunca se expone `pdf_stored_name` al usuario.

## 4. Templates y variables

Templates:

- identidad separada de versión;
- versión inmutable;
- contenido plain UTF-8, no HTML/CSS/JS/PHP;
- cambio de contenido = nueva versión server-side;
- desactivar una plantilla impide nuevos drafts, pero no invalida un draft ya fijado a una versión histórica.

Placeholders:

- sintaxis simple `{{namespace.key}}`;
- allowlist de variables automáticas;
- variables manuales únicamente bajo namespace `custom`;
- sin funciones, loops, condiciones, eval, reflexión ni SQL dinámico;
- valores escapados antes de construir HTML interno.

Fechas contractuales:

- `start_date`, `end_date`, `duration_text` se introducen/confirman explícitamente;
- F7 no infiere fecha legal final desde “N meses”.

## 5. Draft, preview y elegibilidad

Crear draft exige relectura de fuentes canónicas:

- candidato existente y `pending_screening`;
- screening existente y `approved`;
- unidad canónica del candidato;
- unidad `available|in_process`;
- propiedad activa;
- tipo unidad/documento compatible;
- plantilla compatible activa con al menos una versión;
- no draft activo previo;
- no contrato finalizado previo para ese candidato.

La creación serializa por candidato para impedir dobles drafts por carrera.

Preview:

- solo `draft`;
- no crea PDF;
- no muta estado;
- usa la misma resolución segura que generación;
- marca visible `BORRADOR`;
- no confía HTML del usuario.

## 6. Snapshot, generación e inmutabilidad

`generate()`:

1. exige `draft`;
2. relee candidato/screening/unidad/propiedad;
3. confirma vínculo canónico candidato-unidad;
4. resuelve variables;
5. construye HTML interno escapado;
6. renderiza PDF;
7. valida firma/tamaño;
8. calcula SHA-256 exacto;
9. persiste evidencia y pasa atómicamente a `generated`.

Después de `generated` quedan congelados:

- candidate/unit/template version/document type;
- canon contractual y administración;
- fechas y duración;
- variables resueltas;
- variables manuales;
- anexos;
- snapshot HTML;
- PDF, tamaño y SHA-256;
- `generated_at`.

Solo `tasks_json` puede cambiar en `draft|generated`; las tareas no forman parte de la evidencia contractual congelada.

Un fallo de render, escritura o persistencia deja el contrato en `draft` y limpia archivos temporales/parciales.

## 7. Finalización y contexto candidato

`finalize()`:

- exige `generated`;
- bloquea por candidato;
- rechaza candidato `withdrawn`;
- impide segundo contrato `finalized` para el mismo candidato;
- añade únicamente estado final, usuario y timestamp;
- no crea tenant/lease/user;
- no cambia `candidates.status`;
- no cambia `units.status`;
- no representa firma electrónica/digital.

El candidate detail recibe contexto contractual únicamente delegando en `ContractService` y solo se muestra a `contracts.view`/owner.

La CTA de creación exige una plantilla compatible activa con versión real; no muestra acción muerta.
