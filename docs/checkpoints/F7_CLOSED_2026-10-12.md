## 1. Resultado F7

F7 implementa un motor contractual privado y mínimo sobre las fuentes canónicas existentes:

`candidate + screening approved + unit → draft → safe preview → immutable snapshot → private PDF + SHA-256 → finalized`

F7 **no** crea tenant, lease, usuario de inquilino, ocupación automática, firma electrónica/digital, segundo auth ni catálogo paralelo.

Tipos V1 exactos:

- `urban_housing`;
- `independent_parking`.

Estados contractuales exactos:

`draft → generated → finalized`

`finalized` es terminal dentro de F7.

## 3. Runtime y PDF

F7 soporta PHP `>=8.3 <8.6` con PDO/pdo_mysql, mbstring, fileinfo, dom y gd.

Dompdf permanece bloqueado en `3.1.6`, con recursos remotos deshabilitados, sin shell ni binarios externos.

Los PDFs:

- viven en `storage/contracts/` fuera de exposición HTTP directa;
- usan nombre aleatorio `32 hex + .pdf` sin PII;
- se verifican antes del rename final;
- límite máximo `10 MiB`;
- guardan tamaño y SHA-256 exactos;
- `privatePdf()` revalida nombre, realpath, `%PDF-`, tamaño y hash antes de servir;
- `pdf_stored_name` no se expone al usuario.

Además, el root `.gitignore` ignora todo `/storage/` para impedir que PDFs, documentos de candidatos, media o branding de runtime entren al repositorio por un `git add` accidental.

## 4. Templates, variables y capacidad

Templates:

- identidad separada de versión;
- versión inmutable;
- plain UTF-8, no HTML/CSS/JS/PHP;
- cambio de contenido = nueva versión server-side;
- desactivar plantilla bloquea nuevos drafts, no invalida un draft histórico ya fijado.

Placeholders:

- sintaxis `{{namespace.key}}`;
- allowlist automática;
- manuales solo `custom.*`;
- sin funciones, loops, condiciones, eval, reflexión ni SQL dinámico;
- valores escapados antes de construir HTML interno.

Capacidad final del contrato:

- `manual_variables_json`: `LONGTEXT`, porque el presupuesto aprobado de hasta 50 valores de hasta 4.000 caracteres puede superar `TEXT`;
- `tasks_json`: `TEXT`, suficiente para su límite aprobado;
- `annexes_json`: `LONGTEXT`, porque las notas no tienen un límite aprobado que garantice caber en `TEXT`;
- `resolved_variables_json` y `snapshot_html`: `LONGTEXT`.

No se inventaron límites funcionales nuevos para adaptar el producto al esquema.

## 5. Draft, preview y elegibilidad

Crear draft exige relectura de las fuentes canónicas:

- candidato existente y `pending_screening`;
- screening existente y `approved`;
- unidad canónica del candidato;
- unidad `available|in_process`;
- propiedad activa;
- tipo unidad/documento compatible;
- plantilla compatible activa con versión;
- no draft activo previo;
- no contrato finalizado previo para ese candidato.

La creación serializa por candidato para impedir dobles drafts.

Preview:

- solo `draft`;
- no crea PDF ni muta estado;
- usa la misma resolución segura;
- marca visible `BORRADOR`;
- no confía HTML del usuario.

## 6. Snapshot, generación, concurrencia e inmutabilidad

`generate()` final:

1. exige `draft`;
2. abre transacción;
3. bloquea la fila contractual con `FOR UPDATE` **antes** de congelar evidencia;
4. relee el contrato dentro de la misma transacción;
5. relee candidato/screening/unidad/propiedad y confirma el vínculo canónico;
6. resuelve variables y construye HTML interno escapado;
7. renderiza y valida PDF;
8. calcula tamaño y SHA-256 exactos;
9. persiste snapshot/PDF/hash y cambia atómicamente a `generated`;
10. ante error hace rollback y limpia temporales/parciales.

Este orden cierra la ventana de carrera entre `updateDraft()` y `generate()` que podía producir fila nueva con PDF/snapshot viejo.

Después de `generated` quedan congelados candidate/unit/template version/document type, economía, fechas, duración, variables, anexos, snapshot, PDF, tamaño, hash y `generated_at`.

Solo `tasks_json` puede cambiar en `draft|generated`; las tareas no forman parte de la evidencia contractual congelada.

## 7. Finalización

`finalize()`:

- exige `generated`;
- serializa por candidato;
- rechaza candidato `withdrawn`;
- impide segundo `finalized` para el mismo candidato;
- añade únicamente estado final, usuario y timestamp;
- no crea tenant/lease/user;
- no cambia `candidates.status` ni `units.status`;
- no representa firma electrónica/digital.
